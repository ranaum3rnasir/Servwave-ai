# Lead Test Data Rules

The Lead model tracks the customer journey from first contact through to won/lost/cancelled. Every test fixture must respect the status state machine, required fields per status, and cascade rules defined here.

## 1. Status State Machine

```
NEW → CONTACTED → WALKTHROUGH_SCHEDULED → WALKTHROUGH_COMPLETED → ESTIMATED → WON
 \        \               \                                                    \
  → CANCELLED  → CANCELLED  → CANCELLED (reverts to CONTACTED)         → LOST → CANCELLED
```

Terminal statuses: **WON**, **LOST**, **CANCELLED** -- cannot transition out.

## 2. Required Fields Per Status

| Status | Required Fields (must be set) | Must Be Null |
|--------|-------------------------------|-------------|
| NEW | `customer_id`, `service_request` | `contacted_at`, `walkthrough_scheduled_at`, `walkthrough_completed_at`, `lost_at`, `lost_reason`, `cancelled_at`, `cancelled_reason` |
| CONTACTED | +`contacted_at` (realistic note) | `walkthrough_scheduled_at`, `walkthrough_completed_at`, `lost_*`, `cancelled_*` |
| WALKTHROUGH_SCHEDULED | +`walkthrough_scheduled_at`, +`walkthrough_assigned_to` (SALES or TECHNICIAN user), +`walkthrough_duration_minutes` (15-480) | `walkthrough_completed_at`, `lost_*`, `cancelled_*` |
| WALKTHROUGH_COMPLETED | +`walkthrough_completed_at` | `lost_*`, `cancelled_*` |
| ESTIMATED | (at least 1 SENT estimate exists on this lead) | `lost_*`, `cancelled_*` |
| WON | (at least 1 APPROVED estimate) | `lost_*`, `cancelled_*` |
| LOST | +`lost_at`, +`lost_reason` (specific reason) | `cancelled_*` |
| CANCELLED | +`cancelled_at`, +`cancelled_reason` (specific reason) | `lost_*` |

Note: `walkthrough_needed` defaults to `true`. If set to `false`, walkthrough steps can be skipped.

## 3. Walkthrough Cancellation Special Case

When a walkthrough is cancelled from WALKTHROUGH_SCHEDULED, the lead **reverts to CONTACTED** (not to a new status). Required fields for the cancellation:

- `walkthrough_cancelled_at` -- when it was cancelled
- `walkthrough_cancelled_reason` -- why (e.g., "Customer rescheduled", "Tech unavailable")
- `walkthrough_cancelled_by` -- user who cancelled

The previous walkthrough fields (`walkthrough_scheduled_at`, `walkthrough_assigned_to`) remain populated as historical record. They are NOT nulled out.

## 4. Field Generation Rules

- `lead_number`: Auto-generated by API (format L00001). Never hardcode in E2E tests. Backend fixtures can use mock values.
- `assigned_to`: Must reference a user with role SALES or ADMIN. Typically SALES.
- `walkthrough_assigned_to`: Must reference SALES or TECHNICIAN user. Cannot be DISPATCHER.
- `service_request`: Use realistic descriptions from service request patterns. Never "test request" or "E2E test".
- `service_address_*`: Copy from customer's primary service location, or specify if different job site.
- `contacted_note`: Brief note about the call (e.g., "Spoke with homeowner, confirmed AC issue started last week. Available for walkthrough any weekday afternoon.")
- `walkthrough_notes`: Detailed observations (e.g., "Unit is 15 years old, Trane XR15. Compressor cycling every 3 minutes. Refrigerant likely low. Ductwork in good condition.")
- `lost_reason`: Specific reason (e.g., "Customer went with competitor quote -- $200 cheaper", "Customer decided to wait until spring", "Property sold")
- `cancelled_reason`: Specific reason (e.g., "Customer moved out of service area", "Duplicate lead -- merged with L00042")

## 5. Cascade Rules

- Cancelling a lead auto-cancels all active (DRAFT/SENT/PENDING) estimates on that lead.
- Cancelling a lead auto-voids any REQUESTED deposits.
- Mark-as-lost does NOT cascade -- estimates and jobs remain in their current state.

## 6. Invalid Data for Testing

| # | Violation | Description | Expected Result |
|---|-----------|-------------|-----------------|
| L-01 | CONTACTED without contacted_at | Status is CONTACTED but contacted_at is null | Should fail validation |
| L-02 | WALKTHROUGH_SCHEDULED without walkthrough_assigned_to | Missing performer | Should fail |
| L-03 | WALKTHROUGH_SCHEDULED with DISPATCHER as walkthrough_assigned_to | Wrong role | Should fail |
| L-04 | walkthrough_completed_at < walkthrough_scheduled_at | Completed before scheduled | Temporal violation |
| L-05 | contacted_at < created_at | Contacted before lead existed | Temporal violation |
| L-06 | LOST without lost_reason | Empty/null reason | Should require reason |
| L-07 | CANCELLED without cancelled_reason | Empty/null reason | Should require reason |
| L-08 | Transition from NEW directly to WALKTHROUGH_SCHEDULED | Skip CONTACTED step | Should fail transition |
| L-09 | walkthrough_duration_minutes: 0 | Invalid duration | Should fail (min 15) |
| L-10 | walkthrough_duration_minutes: 600 | Too long | Should fail (max 480) |
| L-11 | walkthrough_needed=false while status WALKTHROUGH_SCHEDULED | Contradictory state | Should fail |
| L-12 | Transition from WON to CONTACTED | Terminal status | Should fail |
| L-13 | Transition from LOST to NEW | Terminal status | Should fail |
| L-14 | assigned_to pointing to TECHNICIAN | Wrong role for lead assignment | Should fail |
| L-15 | Missing customer_id | Lead without customer | Should fail creation |
| L-16 | Missing service_request | Lead without description | Should fail creation |
