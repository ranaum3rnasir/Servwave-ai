## Phase 1: Database Migration & Data Migration — L
### Depends on: None
### What's built: Backend (Prisma schema + migration)

This is the foundational phase. Everything else depends on the schema being correct.

### Files modified:
- `backend/prisma/schema.prisma`

### Files created:
- `backend/prisma/migrations/XXXXXX_walkthrough_module/migration.sql` (auto-generated by `prisma migrate dev`)

### Changes:

**1a. LeadStatus Enum**
- Remove: `ESTIMATING`, `APPROVED`
- Add: `WALKTHROUGH_COMPLETED`
- Final values: `NEW, CONTACTED, WALKTHROUGH_SCHEDULED, WALKTHROUGH_COMPLETED, ESTIMATED, WON, LOST, CANCELLED`

**1b. Lead Model — New Fields**
```prisma
lead_number               String    @unique
walkthrough_assigned_to   String?   @db.Uuid
walkthrough_needed        Boolean   @default(true)
walkthrough_cancelled_at  DateTime?
walkthrough_cancelled_reason String?
walkthrough_cancelled_by  String?   @db.Uuid
contacted_at              DateTime?
contacted_note            String?
```
- Add FK relations: `walkthrough_performer User? @relation("LeadWalkthroughPerformer", ...)` and `walkthrough_canceller User? @relation("LeadWalkthroughCancelledBy", ...)`
- Add corresponding reverse relations on `User` model

**1c. Job Model — New Fields**
```prisma
walkthrough_notes         String?
walkthrough_completed_at  DateTime?
walkthrough_assigned_to   String?   @db.Uuid
```
- Add FK relation for walkthrough_assigned_to on User

**1d. Attachment Model — New Fields**
```prisma
display_name  String
description   String    @default("")
context       AttachmentContext @default(OTHER)
```

**1e. New Enum: AttachmentContext**
```prisma
enum AttachmentContext {
  WALKTHROUGH
  JOB_WORK
  ESTIMATE
  OTHER
}
```

**1f. Data Migration (in migration SQL)**
- `UPDATE leads SET status = 'WALKTHROUGH_COMPLETED' WHERE status = 'ESTIMATING'`
- `UPDATE leads SET status = 'WON' WHERE status = 'APPROVED'`
- `UPDATE attachments SET display_name = file_name, description = '', context = 'OTHER'`
- Backfill `lead_number`: sequential `LEAD-{year}-NNNN` ordered by `created_at`
- Set `walkthrough_needed = true` for all existing leads

**IMPORTANT MIGRATION NOTE:** PostgreSQL enums require special handling. Cannot directly remove enum values in Prisma migrations. The migration SQL will need to:
1. Create a new enum type with the correct values
2. Alter the column to use the new type
3. Drop the old type

### Acceptance criteria:
- `npx prisma validate` passes
- `npx prisma migrate dev` runs successfully
- Existing data migrated correctly (ESTIMATING -> WALKTHROUGH_COMPLETED, APPROVED -> WON)
- All existing attachments have display_name = file_name, context = OTHER
- All existing leads have walkthrough_needed = true and a lead_number

### Testing:
- Manual validation via `npx prisma studio` or direct SQL queries
- Existing backend test suite still passes (after test setup updates in Phase 7)

## Phase 2: Lead Walkthrough API — L
### Depends on: Phase 1
### What's built: Backend (controller + routes)

### Files modified:
- `backend/src/controllers/lead.controller.ts` — heavy modification
- `backend/src/routes/lead.routes.ts` — add new routes

### Changes:

**2a. New endpoint: POST /api/leads/:id/contact**
- Schema: `{ contacted_at: datetime, contacted_note?: string }`
- Guard: status must be NEW
- Effect: set contacted_at + contacted_note, transition to CONTACTED
- Sales guard: own leads only
- Timeline event logged

**2b. New endpoint: POST /api/leads/:id/walkthrough/schedule**
- Schema: `{ walkthrough_scheduled_at: datetime, walkthrough_assigned_to: uuid, walkthrough_duration_minutes: number, send_email?: boolean, force?: boolean }`
- Guard: status must be CONTACTED or WALKTHROUGH_COMPLETED
- Conflict detection: query Job + Lead tables for performer overlap
- Effect: set walkthrough fields, transition to WALKTHROUGH_SCHEDULED
- Timeline event logged
- Walkthrough performer defaults to assigned_to if not provided

**2c. New endpoint: POST /api/leads/:id/walkthrough/complete**
- Schema: `{}` (empty body, server-side timestamp)
- Guard: status must be WALKTHROUGH_SCHEDULED
- Permission: Admin, Dispatcher, or the walkthrough performer
- Effect: set walkthrough_completed_at = now(), transition to WALKTHROUGH_COMPLETED
- Timeline event logged

**2d. New endpoint: POST /api/leads/:id/walkthrough/cancel**
- Schema: `{ cancelled_reason: string }`
- Guard: status must be WALKTHROUGH_SCHEDULED
- Effect: set cancelled fields, clear walkthrough_scheduled_at, set walkthrough_needed = true (unlock), revert to CONTACTED
- Timeline event logged

**2e. Modify: POST /api/leads (create)**
- Auto-generate `lead_number` using `LEAD-YYYY-NNNN` pattern (same pattern as job/estimate numbering)
- Accept `walkthrough_needed` field (default true)

**2f. Modify: POST /api/leads/:id/walkthrough (existing)**
- Repurpose as general walkthrough field updates (notes, duration changes only)
- Remove status auto-transitions from this endpoint
- Remove scheduled_at/completed_at from this endpoint's schema (those go through dedicated endpoints)

**2g. Modify: PATCH /api/leads/:id**
- Allow `walkthrough_needed` toggle
- Block if walkthrough is scheduled (status = WALKTHROUGH_SCHEDULED)

**2h. Modify: POST /api/leads/:id/mark-lost**
- If lead status = WALKTHROUGH_SCHEDULED, auto-cancel walkthrough
- Set cancellation fields, revert walkthrough_needed = true

**2i. Modify: GET /api/leads (list)**
- Include `walkthrough_assigned_to` and `walkthrough_needed` in `leadListSelect`
- Include `contacted_at` in `leadListSelect`
- Include `lead_number` in both list and detail selects
- Add walkthrough status filter param (e.g., `walkthrough_status=needs_scheduling|scheduled|completed|not_needed`)
- Update stats queries: replace ESTIMATING references with new statuses

**2j. Modify: GET /api/leads/:id**
- Include new fields in `leadDetailSelect`: `lead_number`, `walkthrough_assigned_to`, `walkthrough_needed`, `walkthrough_cancelled_at`, `walkthrough_cancelled_reason`, `walkthrough_cancelled_by`, `contacted_at`, `contacted_note`
- Include walkthrough performer relation

### Acceptance criteria:
- POST /api/leads/:id/contact: NEW -> CONTACTED works, non-NEW returns 400
- POST /api/leads/:id/walkthrough/schedule: CONTACTED -> WALKTHROUGH_SCHEDULED works, conflict returns 409
- POST /api/leads/:id/walkthrough/complete: WALKTHROUGH_SCHEDULED -> WALKTHROUGH_COMPLETED works
- POST /api/leads/:id/walkthrough/cancel: WALKTHROUGH_SCHEDULED -> CONTACTED works, fields cleared
- Lead creation generates lead_number
- Mark-lost auto-cancels walkthrough
- All invalid transitions return 400

### Testing:
- Covered in Phase 7 (consolidated backend tests)

### Changes:

**5a. New attachment routes (polymorphic)**
Pattern: `/api/attachments/:entityType/:entityId`
- `POST /api/attachments/:entityType/:entityId` — upload file (multipart/form-data)
- `GET /api/attachments/:entityType/:entityId` — list attachments for entity
- `PATCH /api/attachments/:entityType/:entityId/:attachmentId` — update display_name/description
- `DELETE /api/attachments/:entityType/:entityId/:attachmentId` — delete file + record

**5b. Supabase Storage integration**
- Upload to bucket: `attachments/{entityType}/{entityId}/{uuid}-{filename}`
- Generate signed URL or public URL depending on bucket config
- Validate file type: JPG, PNG, HEIC, MP4, PDF
- Validate file size: 25MB per file
- Validate total entity size: 200MB per entity (sum existing + new)

**5c. Multipart parsing**
- Add `multer` middleware for multipart/form-data parsing
- Extract: file buffer + display_name + description + context fields from form data

**5d. Entity access control**
- Validate entityType is valid AttachmentEntity
- Validate entity exists
- Check role-based access (Admin/Dispatcher: all, Sales: own leads, Tech: own jobs)

**5e. Timeline events**
- Log attachment uploaded/deleted/updated events

### Acceptance criteria:
- Can upload a file to any entity type
- File appears in Supabase Storage
- Attachment record created with display_name, description, context
- Can list attachments for an entity (grouped by context)
- Can update display_name and description
- Can delete attachment (removes from storage + DB)
- 25MB file limit enforced
- Invalid file types rejected
- Timeline events logged
