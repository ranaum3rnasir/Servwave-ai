## What slice 1 actually delivers

Working end to end: an admin creates a TEXT field in Settings -> Custom Fields, picks its entity
types, and the Job detail page renders an "Extra Info" card that reads and writes
`jobs.custom_fields` (JSONB, keyed by definition UUID so a rename cannot orphan a value).

Deliberately inert in slice 1, so do not treat these as bugs:

- `type` is hard-locked to TEXT - `z.literal('TEXT')` in `custom-field-definitions.controller.ts`,
  and `CustomFieldsPage.tsx` hardcodes `type: 'TEXT'`. The other four enum values exist but are
  unreachable. Slice 2.
- `required` and `sort_order` are columns with no writer. `archived_at` exists with no UI. Slice 6.

## The one real defect - CLOSED 2026-08-07

**Was:** an admin could tick Lead, Customer, or Price Book Item on a definition and it silently
did nothing. The settings form offered all four entity types and the `custom_fields` column
existed on all four tables, but only the Job controller accepted a `custom_fields` patch and
`ExtraInfoPanel` was mounted only on `JobDetailPage.tsx`. The definition saved, appeared in the
list, and surfaced nowhere - no error, no empty state, no hint.

Closed by doing both halves rather than only the cheap one:

- **Lead and Customer became real** (slice 3). Both PATCH endpoints validate and merge
  `custom_fields`, both detail selects return the bag, and `ExtraInfoPanel` mounts on both pages.
- **Price Book Items was removed from the form** until slice 5 builds its surface. The rule this
  encodes: an entity option exists only once something renders it.

The panel moved to `frontend/src/components/custom-fields/ExtraInfoPanel.tsx` (it is no longer
job-specific) and grew a `variant` prop - `'card'` keeps the Job Command Center's SectionCard
chrome, `'plain'` is a bare section for the Lead/Customer unified-card layout, where a nested
card would read as a card inside a card. Slice 5's dialog host is the third consumer of
`'plain'`, so that wrinkle is already solved.

Also added: **PATCH `/api/custom-field-definitions/:id`** (label + entity scope). Slice 3 requires
the scope be editable after creation, and there is no DELETE by design, so without this an admin
who ticked the wrong entity had to abandon the key and invent a second one. Narrowing the scope
writes only the definition row - values live in each entity's own JSONB bag, so a dropped entity
stops rendering and reinstating it brings the values straight back. That is pinned by a test.

## Known rough edges, none fixed

Found by reading the slice-1 code. All are small and none block the next slice:

- Two concurrent creates of the same key return **500**, not 409 - the `@@unique([organization_id,
  key])` violation is not caught and mapped.
- No max length on a TEXT value, and no per-org cap on the number of definitions.
- No delete path at all, by design (archive-only), but slice 6 still owes the UI.
- The Extra Info panel has its own Save button per entity, separate from the page's other save
  affordances. Fine on the Job page (a column of independently-saving cards); slightly odd in the
  Lead and Customer sidebars. Left alone rather than reworked mid-slice.
- Editing a definition whose scope includes PRICE_BOOK_ITEM preserves that scope, but the form
  cannot show it - the checkbox is gone until slice 5. No org has such a definition today; worth
  remembering if one appears before slice 5 lands.

## RLS work that landed alongside this, and what it means for you

`rls-coverage.test.ts` now runs in the CI `Database (migrations + RLS)` job and **fails the build
if any table with an `organization_id` lacks the `tenant_isolation` policy.** Slices 3 and 5 add
no new tables, so this should not fire - but if a later slice does add one, that is what the red
means, and the fix is a migration, not an exemption.

`email_suppressions` is the single deliberate exemption in `GLOBAL_BY_DESIGN`. Do not "fix" it: a
hard bounce belongs to the address, not the org, and tenant-scoping it would make the suppression
gate re-mail bounced addresses.

Verified on staging after the #1378 deploy (migration applied 16:57:19Z, 81s after merge): all
four tables `rls_on=true, forced=true` with policy expressions byte-identical to `jobs`, and
exactly **1** org-scoped table without RLS - the intended exemption.

## Working constraints that bit during this session

  is still non-zero, so a `main`-based branch shows thousands of phantom files.
- The backend suite flakes ~1 test in 8035 under local load, a **different** test each run
  (`invoices`, then `inv-audit-sweep`); each passes in isolation. Documented in `vitest.config.ts`.
  Do not chase it - check CI, which passes.
- The frontend report tests (`payment-fees-report`, `inventory-usage-report`,
  `reports-plan-gating`) time out locally on a lazy import but pass in CI. Same advice.
